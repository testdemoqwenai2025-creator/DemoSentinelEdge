Functional Tests
Happy-path + basic failure tests — must pass on every PR + nightly
5 tests
functional-1
Valid telemetry accepted
every PR
Send a well-formed Avro message with valid schema, valid types, in-range values, sensible timestamp. Verify it lands in TimescaleDB within 2 sec (P95).
Implementation: pytest + confluent-kafka Python producer. Send 1000 valid messages to mqtt-ingest topic. Assert all 1000 appear in TimescaleDB within 2 sec. Assert zero in dead-letter topic.
Acceptance: 100% of valid messages persisted < 2 sec P95. 0% in dead-letter. 0% data loss.
Edge cases: Missing fieldsInvalid typeFuture timestampRange violation
Build plan: Phase 1 — Foundation
functional-2
Invalid telemetry quarantined
every PR
Send malformed messages (wrong Avro schema, missing required fields, invalid types, future timestamp, range violation). Verify each is routed to dead-letter topic + alert fired.
Implementation: Send 5 categories of malformed messages (10 each). Assert all 50 land in dead-letter. Assert Schema Registry rejects. Assert violation-rate alarm fires when rate > 1%.
Acceptance: 100% of malformed messages quarantined. 0% reach TimescaleDB. Violation-rate alarm fires at > 1%.
Edge cases: Missing fieldsInvalid typeFuture timestampExtreme timestampRange violation
Build plan: Phase 1 — Foundation
functional-3
Duplicates ignored
every PR
Send same message twice (same sensor_id + ts + value_hash) within 100 ms. Verify only one is persisted; the duplicate is silently dropped (logged for diagnosis).
Implementation: Send 100 messages, then resend the same 100 messages. Assert only 100 unique entries in TimescaleDB. Assert duplicate count logged in metrics (Prometheus duplicate_counter).
Acceptance: < 0.01% duplicate rate at 100K msg/sec ingest. Duplicate log entry per drop.
Edge cases: Duplicate messagesReplayed messages
Build plan: Phase 2 — Edge Resilience
functional-4
Late data handled
every PR
Send message with timestamp 10 min in the past (later than Flink watermark window). Verify it lands in Flink side-output (late-events topic), state is updated, no alarm re-trigger unless state changed.
Implementation: Inject 100 messages with ts = now - 10 min into the stream. Assert all 100 appear in late-events Kafka topic. Assert TimescaleDB state is updated for affected sensors. Assert alarm fires only if state changed (e.g. alarm active → cleared).
Acceptance: 100% of late events routed to side-output. State updates correct. No spurious alarm re-fires.
Edge cases: Out-of-order dataLate backfillClock skew
Build plan: Phase 3 — Stream Processing
functional-5
Alerts generated correctly
every PR
Trigger threshold/rate-of-change/duration/multi-condition rules via simulated sensor values. Verify alarms fire with correct priority (high/med/low), correct audit log entry, correct notification routing (email/pager/SCADA).
Implementation: Simulate 5 alarm scenarios: (1) methane > 1% (threshold), (2) reactor T rising > 5°C/min (rate-of-change), (3) bearing T > 90°C for > 5 min (duration), (4) flow low + pressure high (multi-condition), (5) ESD activation (safety-critical). Assert alarm fires within 200 ms (edge) / 5 sec (cloud). Assert audit log entry created. Assert notification routed to correct channel per ISA-18.2 priority.
Acceptance: 100% of triggered alarms fire within SLA. Audit log entries 100% complete. Notifications routed correctly per priority.
Edge cases: Alarm stormCascading failureWrong severity

Edge-Case Tests
Sensor + network + data edge cases — must pass nightly
10 tests
edge-case-1
Sensor stuck
nightly
Generate a constant value (zero variance) for > N hours (configurable per sensor type — 1h for vibration, 30 min for SpO2). Verify stuck-value detector fires.
Implementation: Device simulator: set sensor to constant 50.0 for 65 min. Assert stuck-value alarm fires at 60 min. Assert alarm has correct citation chain (zero variance > 60 min). Assert alarm auto-clears when value changes.
Acceptance: Stuck-value alarm fires at configured threshold. Auto-clears when value changes. < 1% false-positive rate (no alarm for naturally-stable sensors).
Edge cases: Stuck valueSensor deadSensor physically blocked
Build plan: Phase 2 — Edge Resilience
edge-case-2
Sensor drift
nightly
Generate a slowly-drifting value (e.g. +0.5°C/day on a thermocouple). Verify drift detection fires when drift exceeds threshold (e.g. 5% from baseline).
Implementation: Device simulator: linear drift 0.5°C/day for 14 days. Compress to 14-hour test (12x speedup). Assert drift alarm fires at day 10 (5% threshold). Assert self-calibration mesh corrects (cross-check with 2 redundant sensors).
Acceptance: Drift alarm fires within 24h of threshold breach. Self-calibration correction within 5% of true value.
Edge cases: Sensor driftCalibration expired
Build plan: Phase 2 — Edge Resilience (drift detection) + Phase 4 (self-calibration)
edge-case-3
Timestamp future
nightly
Send message with timestamp 10 min in the future (beyond 5-min tolerance). Verify rejected + quarantined. Send message 2 min in future (within tolerance) — verify accepted.
Implementation: Send 50 messages with ts = now + 10 min (rejected) and 50 with ts = now + 2 min (accepted). Assert 50 in dead-letter, 50 in TimescaleDB. Assert clock-skew alert fires for the 10-min-future batch.
Acceptance: Future-ts > 5 min: 100% rejected. Future-ts < 5 min: 100% accepted. Clock-skew alert fires for the rejected batch.
Edge cases: Future timestampClock skewClock drift in servers
Build plan: Phase 1 — Foundation (basic check) + Phase 3 (watermark)
edge-case-4
Wrong unit
nightly
Send a message tagged as 'psi' but containing the numeric value of Pa (e.g. 5000 instead of 70 psi). Verify LLM-assisted unit normalization + physics sanity check catches it.
Implementation: Send a pressure reading of 5000 tagged as 'psi' (impossible — wellhead pressure is 1000-5000 psi, but 5000 Pa = 0.7 psi is way below range). Assert rejected by physics check. Assert unit-mismatch alarm fires.
Acceptance: 100% of unit-mismatched messages rejected by physics check. Unit-mismatch alarm fires with correct citation (expected range vs received value).
Edge cases: Wrong unitUnit mismatchRange violation
Build plan: Phase 1 — Foundation (schema) + Phase 3 (enrichment + physics check)
edge-case-5
Gateway offline
weekly
Kill the edge gateway (process kill, not graceful shutdown). Verify SQLite buffer continues filling, no data loss. Restart gateway after 1h. Verify buffer replays to cloud with no duplicates.
Implementation: SIGKILL the edge runtime. Generate telemetry for 1h (sensor simulator continues). Restart gateway. Assert SQLite buffer has 1h of data. Assert replay to cloud completes within 4h. Assert idempotency: 0 duplicates in cloud TimescaleDB.
Acceptance: 0 data loss during 1h gateway-down. Replay completes within 4h. 0 duplicates.
Edge cases: Gateway failureNetwork outageBuffer overflow
Build plan: Phase 2 — Edge Resilience

weekly

Implementation: SIGKILL EMQX primary. Send 1000 messages during failover window. Assert all 1000 persisted. Assert client reconnect within 30 sec. Assert alert fired (broker-down).
Acceptance: Failover < 10 sec. 0 message loss during failover. Clients reconnect < 30 sec.
Edge cases: MQTT broker failureNetwork outage
Build plan: Phase 5 — Hardening (failover drills)

weekly

Acceptance: Circuit Breaker engages. HPA scales within 5 min. Lag stabilizes. 0 crashes. 0 data loss (overflows to dead-letter if needed).
Edge cases: BackpressureStream processor crashStorage full
Build plan: Phase 3 — Stream Processing + Phase 5 (chaos)

weekly
Random kill of 1 EMQX broker in 3-node cluster. Verify cluster heals < 30 sec. Verify no message loss. Verify client reconnect succeeds.
Implementation: Litmus chaos experiment: kill 1 of 3 EMQX brokers at random time. SLO: cluster heals < 30 sec, 0 message loss, all clients reconnect < 60 sec. Auto-rollback if SLO breached.
Acceptance: Cluster heals < 30 sec. 0 message loss. All clients reconnect < 60 sec.
Edge cases: MQTT broker failureNetwork outage

Implementation: Litmus: kill 1 Flink TM. Verify Flink job restarts from checkpoint < 5 min. Verify 0 duplicate output. Verify 0 data loss. Verify checkpoint success metric recovers.
Acceptance: Restart < 5 min. 0 duplicates. 0 data loss. Checkpoint metric recovers.
Edge cases: Stream processor crashDatabase failure
Build plan: Phase 5 — Hardening (chaos tests)

Acceptance: K8s quorum maintains. App pods rescheduled < 5 min. Partition heals < 1 min after restore.
Edge cases: Network outageRegion outageMan-in-the-middle

Safety Validation
Formal safety engineering techniques — required for IEC 61511 / ISO 26262 / IEC 62304 certification
6 tests
safety-1
HAZOP (Hazard and Operability Study)
annual
Structured technique: identify process hazards via guidewords (No, More, Less, Reverse, As Well As, Other Than) applied to each process parameter. Document deviations + causes + consequences + safeguards + recommendations.
Implementation: HAZOP workshop: 3-day facilitated session with process engineers + safety engineer + operator. Use HAZOP software (Phast or Hazop+). Output: HAZOP worksheet with 200+ deviations documented. Map each deviation to SentinelEdge alarm/rule + SIS safety layer. Verify platform catches each HAZOP-identified hazard.
Acceptance: HAZOP worksheet complete (200+ deviations). Each hazard mapped to platform alarm. Platform catches 100% of HAZOP-identified hazards (or SIS catches, with platform advisory).
Edge cases: Dangerous conditionCascading failureFalse negative
Build plan: Phase 5 — Hardening (safety validation)
safety-2
FMEA (Failure Modes and Effects Analysis)
annual
Systematic technique: for each component, list failure modes + effects + severity + occurrence + detection + RPN (Risk Priority Number = S × O × D). Address high-RPN failures.
Implementation: FMEA workshop: 2-day session with engineering team. Use FMEA software (ReliaSoft or Excel template). Output: FMEA worksheet with 100+ failure modes documented. Compute RPN for each. Address all RPN > 100 (or per sector threshold). Verify platform mitigates each high-RPN failure mode.
Acceptance: FMEA worksheet complete (100+ failure modes). All RPN > 100 addressed. Platform mitigates each.
Edge cases: Sensor deadSensor driftGateway failureDatabase failure
Build plan: Phase 5 — Hardening (safety validation)
safety-3
STPA (System-Theoretic Process Analysis)
annual
Modern technique for cyber-physical systems: identify unsafe control actions (UCAs) — control actions that, in given contexts, lead to hazards. Map to controller constraints + scenarios.
Implementation: STPA workshop: 3-day session with system engineers + safety engineer. Output: STPA worksheet with 50+ UCAs identified. Define controller constraints for each UCA. Verify platform enforces each constraint. (STPA catches hazards HAZOP misses — software-caused, controller-caused.)
Acceptance: STPA worksheet complete (50+ UCAs). Each UCA has controller constraint. Platform enforces 100% of constraints.
Edge cases: System recommends unsafe actionAutomated control without certificationOperator ignores alert
Build plan: Phase 5 — Hardening (safety validation)
safety-4
Alarm rationalization review
annual
Per ISA-18.2: review every alarm for necessity, uniqueness, priority, setpoint, on-delay, off-delay, description, cause, consequence, corrective action. Target: < 10 alarms/operator/shift.
Implementation: Rationalization workshop: 5-day session with operators + process engineers. Review all 500+ alarms. For each: decide keep/modify/remove. Document rationalization. Update alarm config. Post-implementation: monitor alarm rate for 30 days. Target < 10/operator/shift.
Acceptance: All alarms rationalized. Alarm rate < 10/operator/shift (down from typical 100+ baseline).
Edge cases: Alarm fatigueWrong severityOperator misreads dashboard
Build plan: Phase 5 — Hardening (operator UX)
safety-5
Operator-in-the-loop testing
quarterly
Shadow sessions with real operators. Run simulations, observe operator response. System Usability Scale (SUS) survey target > 80. Verify operator can acknowledge, diagnose, respond to alarms within SLA.
Implementation: 10+ shadow sessions per design partner. Each session: 1h with 5 simulated alarm scenarios. Observe: time-to-acknowledge, time-to-diagnose, time-to-respond. Post-session SUS survey. Target: SUS > 80, mean acknowledge < 30 sec, mean diagnose < 2 min.
Acceptance: SUS > 80. Time-to-ack < 30 sec. Time-to-diagnose < 2 min. 90%+ correct response to alarms.
Edge cases: Operator misreads dashboardTraining gapAlarm fatigue
Build plan: Phase 5 — Hardening (operator UX validation)
safety-6
Incident replay
quarterly
Replay historical incidents (from CMMS, regulator reports, public incident databases). Verify platform detects + responds correctly. Backtest on 90 days of historical data.
Implementation: Replay 10 historical incidents (e.g. Macondo, T2 Laboratories, Upper Big Branch, Northeast Blackout, Milwaukee Crypto, Flint MI). For each: replay sensor data through platform. Verify platform detects anomaly + fires alarm + recommends correct action. Compute detection time vs actual incident time.
Acceptance: Platform detects 100% of replayed incidents. Detection time < actual incident discovery time (catches earlier). Recommended action matches actual corrective action.
Edge cases: False negativeRare eventCold startIncident investigation
Build plan: Phase 4 — ML (backtest) + Phase 5 (validation)
