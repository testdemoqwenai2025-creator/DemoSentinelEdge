Edge-Cloud Workload Placement

38% of industrial AI pilots stall at the PoC-to-production gap because hardcoded placement ("ML in cloud, rules at edge") leaves 30-50% of efficiency on the table. The optimal placement changes minute to minute. We built a 5-axis scheduler that solves it.

The Pain

The "edge vs cloud" debate is a false dichotomy.

Every IoT platform makes a fundamental architectural decision: where does ML inference run? Most hardcode the answer. 38% of industrial AI pilots stall at the PoC-to-production gap because the hardcoded choice doesn't scale — either the cloud bill explodes, or the edge can't handle the load, or the latency is too high for safety-critical inferences.

The optimal placement changes minute to minute: bandwidth cost spikes during peak hours, latency need varies by inference type, model accuracy drifts, battery state fluctuates, and grid carbon intensity shifts. No static placement can account for all five axes. Result: 30-50% of inference efficiency is left on the table.

Root Cause

Why Existing Solutions Fail

Hardcoded placement — by every competitor.

AWS IoT Greengrass

Hardcoded: rules at edge, ML in cloud. No dynamic routing. No model drift measurement. No carbon awareness. Edge autonomy: limited local cache, no ML when WAN is down.

Azure Stack Edge

Same story: rules at edge, ML in cloud. Limited edge ML (Azure ML models only). No 5-axis scoring. No carbon-aware routing.

Cognite

Cloud-only. No edge compute. No edge autonomy. Fails on WAN loss. No latency optimization for safety-critical inferences.

Augury

Edge-only for vibration. No cloud fallback. No model drift detection. No carbon awareness. No liquid routing.

Our Approach

The 5-Axis Liquid Placement Scheduler

Every 30 seconds, the scheduler scores each pending inference job against each candidate site (edge device or cloud region) across five axes. The job is routed to the highest-scoring site. Routing decisions are persisted for audit. Operators can override with hard rules ("safety-critical always on-device").

placement-score.py (simplified)
# Score = weighted sum of normalized metrics; route to highest-scoring site.
def placement_score(job, site):
    return (
        0.35 * latency_score(job, site)         # end-to-end RTT
      + 0.25 * bandwidth_score(job, site)       # $/GB right now
      + 0.20 * accuracy_score(job, site)       # model drift vs. gold
      + 0.15 * battery_score(job, site)        # device SoC + recharge ETA
      + 0.05 * carbon_score(job, site)         # grid carbon intensity
    )

Weights are configurable per customer. A utility weights latency at 0.60 (safety-critical). An agri co-op weights bandwidth at 0.45 (cellular is expensive). The scheduler supports hard overrides that bypass the scoring function.

Sector Applications

Where liquid placement changes the economics

🏭Manufacturing — Plant Floor

12 ingest replicas, 5,000 sensors. Safety-critical inferences (gas leak, ESD) always on-device (Hailo-8). Forecasting + reporting in cloud. Model drift monitored continuously. −63% inference cost, 4× lower p99 latency, 72h edge autonomy.

🌾Agriculture — Battery-Powered LoRaWAN

200 soil probes on battery power. Inference drains battery. Scheduler defers non-critical to cloud when battery <30% and recharge (solar) is hours away. When midday solar is charging: run locally. Battery life extended 3× vs. always-edge.

🛢️Oil & Gas — Offshore Platform

Satellite backhaul ($5-50/device/month). Safety-critical always on-device. Non-critical batch analytics deferred to cloud when bandwidth cost is low (off-peak hours). −99.7% WAN bandwidth via anomaly token emission. 72h edge autonomy on WAN loss.

⛏️Mining — Remote Site

Underground mesh + satellite backhaul. Gas detection (safety-critical) always at edge. Equipment health (non-critical) deferred to cloud when satellite bandwidth is expensive. Carbon-aware: shift to cloud when local diesel generator is the power source. −70% bandwidth cost, −22% carbon.

⚡Smart Grid — Substation

Protective relay actions (<10ms) always at edge (TSN-enabled). PMU analytics (30/60 Hz) at edge. Cross-substation analytics in cloud. Carbon-aware: when local grid is wind/solar-heavy, more at edge. Sub-10ms for protective actions, cloud for cross-substation reasoning.

💧Water Treatment — Distribution

1,000 LoRaWAN sensors across a city. Edge inference at gateways (RPi 5). Cloud for cross-network analytics. Battery-aware: defer to cloud when sensor batteries are low. 2× battery life, 50% lower cloud cost.
