Recommended Production Stack

A complete, opinionated production stack for harsh-environment industrial IoT — from edge hardware to MLOps to observability. Each layer below shows what we recommend, the alternatives we evaluated, and the trade-off reasoning that drove our choices.

Executive summary

We pick cloud-native open-source components wherever possible (Kafka, Flink, Iceberg, TimescaleDB, PostgreSQL, ONNX Runtime, Kubernetes, Prometheus, OpenTelemetry, ArgoCD) so customers can run air-gapped and avoid vendor lock-in. We add Hailo-8 for edge inference, MQTT Sparkplug B for industrial protocol normalization, and a 350M-param TS-FM for zero-shot intelligence — the three layers that distinguish an industrial IoT platform from a generic cloud data platform. Below: 7 layers, ~30 components, with reasoning for each choice.

Edge Layer
Where industrial reality meets digital — sensors, gateways, protocols, local inference
LAYER 1 / 7
Rugged industrial gateways + edge servers
Hardware platform
Customer-supplied x86 + Hailo-8
RecommendedIndustrial x86 (Advantech UNO, OnLogic Factor 201) + NVIDIA Jetson Orin for vision + Hailo-8 (26 TOPS, 2.5 W) for time-series ML. ATEX/IECEx-certified enclosures for Zone 1/Class I Div 2 deployments. Industrial SSD (industrial temp, MLC NAND with PLP). UPS for 8-hour holdover.
AvoidConsumer mini-PCs (Raspberry Pi, Intel NUC) for production — no surge protection, no temperature rating, no compliance path.
Cost driver$800 per Hailo-8 module (one-time); industrial x86 gateway $2K-5K (one-time); Jetson Orin NX $1K (one-time). Compare to Azure Stack Edge $5K+/month lease.
Our reasoning
We chose customer-supplied x86 + Hailo-8 rather than a turnkey edge appliance (e.g., Dell Edge, HPE Edgeline) because: (a) customers in oil & gas / mining already have a vendor for rugged gateways, and forcing a swap blocks sales; (b) Hailo-8 has the best TOPS/W (10.4) of any inference accelerator, which matters when you only have 25 W of power budget on a remote pole; (c) NVIDIA Orin is required only for vision pipelines — TS-FM runs on Hailo. The Hailo-8 is rated -40 to +85°C and supports ATEX Zone 2 (Class I Div 2) — not enough for Zone 1, but most industrial edge deployments live in Zone 2 control rooms. For Zone 1 proper (inside the explosive atmosphere), we use purged enclosures (Ex p) with Zone 2-rated electronics inside — this is the standard pattern in O&G and we recommend it.
Languages: Rust, C++, Python
Edge application development
Rust for runtime, C++ for Hailo, Python for ML
RustEdge runtime — ingest loop, protocol parsers, store-and-forward, scheduler. Memory-safe + zero-cost abstractions; we replaced our initial C++ runtime with Rust in 2024 and cut CVE count by 80%.
C++Hailo-8 inference glue — Hailo SDK is C/C++; ONNX Runtime has C++ bindings; Rust FFI to C++ is straightforward.
PythonML training + edge inference scripts — PyTorch + scikit-learn + Hailo Model Compiler all Python-first. We use Python via PyO3 for edge scripts that benefit from rapid iteration.
Our reasoning
We deliberately do not use Python for the edge runtime loop, despite the productivity benefit, because: (a) Python's GIL + GC pauses make sub-100ms SLAs hard; (b) Python memory footprint is 10-30× larger than Rust for the same logic — matters when you have 512 MB on a Hailo-8 host; (c) Python packaging for offline air-gapped edge is painful (PyInstaller works but produces 80MB binaries). Rust + PyO3 gives us 95% of the productivity of Python with 100% of the runtime safety/perf of C — best of both worlds. We use Python only where ML libraries are unavoidable (training, Hailo Model Compiler, ONNX Runtime) and ship Python code as migration-once frozen binaries (PyO3 + maturin) that don't need a Python interpreter on the edge.
Local buffering: SQLite, DuckDB
Edge data persistence + local analytics
SQLite (hot) + DuckDB (analytical)
SQLiteSingle-file, no DB server, atomic, ACID, WAL mode for concurrent reads — ideal for store-and-forward buffer on edge. Capacity: ~250 GB on consumer SSD before write amplification becomes a concern. Used for: hot sensor readings, alarm queue, audit log.
DuckDBEmbedded analytical OLAP database — runs in-process, no server. Used for: edge-side aggregation queries ("how many alarms in the last 24 hours?"), pre-computing roll-ups before sending to cloud. Co-exists with SQLite (different files).
Our reasoning
We avoid running PostgreSQL or TimescaleDB at the edge despite their query power, because: (a) they need a server process — adds failure modes + ops burden; (b) memory footprint 5-10× larger than SQLite + DuckDB; (c) air-gapped customers don't want to run a DBA at every edge site. SQLite is the world's most-deployed database for a reason — it just works, and our 250 GB store-and-forward buffer is well within its limits. DuckDB for analytics is a 2024-add — it lets us push analytical queries to the edge (e.g., "give me hourly bearing-vibration averages for the last 30 days") without round-tripping to cloud.
Industrial protocols (the connectivity layer)
Talk to brownfield sensors
9 native protocols + Sparkplug B
RecommendedMQTT Sparkplug B (the canonical industrial MQTT — solves the namespace + state-aware problem vanilla MQTT has), OPC UA (modern brownfield), Modbus TCP/RTU (legacy brownfield — still 80% of industrial install base), HART (process instruments over 4-20 mA loops), Foundation Fieldbus (process control), PROFIBUS/PROFINET (discrete manufacturing, German/European dominance), WirelessHART (wireless process instruments — battery-powered mesh), ISA-100.11a (alternative wireless — rare but some chemical + pharma customers require it).
Avoid (or use with care)DNP3 (smart-grid-specific; we support it but only for grid scenarios), IEC 61850 (substation-specific), BACnet (building automation — we explicitly do NOT do this, see "What We Don't Do").
Our reasoning
We support 9 protocols natively rather than relying on a gateway (Kepware, Matrikon, Software Toolbox) because: (a) gateway adds $5K-$20K/year per connector in license fees and a separate vendor relationship; (b) gateway runs on Windows usually — adds a Windows ops burden and a security surface; (c) gateway adds 50-200 ms latency on the path from sensor to ML; (d) we want full control of the schema mapping to feed the LLM-assisted semantic normalizer. Sparkplug B specifically is critical — vanilla MQTT has no concept of session state, so if a sensor disconnects/reconnects, subscribers don't know what the "current" value is until the next publish. Sparkplug B fixes this with a session-aware topic namespace + BIRTH/DEATH/DATA messages. We require all new deployments to use Sparkplug B; we bridge legacy MQTT to Sparkplug B at the edge.
Edge capabilities (the "smart" in smart edge)
Make the edge intelligent, not just a relay
8 edge capabilities
Local rule engineLua + WASM rules — alarm thresholds, simple aggregation. Runs in the Rust runtime. Used for: trip rules, dead-band reporting, alarm acknowledgment.
Store-and-forwardUp to 72 hours of telemetry buffered to SQLite on WAN loss. Replays in correct order with idempotency keys when WAN returns. Critical for offshore + mining scenarios.
CompressionDelta-of-delta encoding for time-series (Gorilla paper), zstd for general payloads. 8-12× compression on vibration data.
Dead-band reportingOnly send if value changed > threshold. Saves 70-90% of bandwidth on slow-changing tags (level, pressure, status).
Duplicate preventionIdempotency key = sensor_id + ts (1ms bucket) + value_hash. Drops duplicates within 100 ms.
Local alertingEdge evaluates alarm rules locally — never round-trips to cloud for safety-critical alerts. Sends to local MQTT broker + SCADA + pager gateway.
Secure bootTPM 2.0 + UEFI Secure Boot + signed boot chain (UEFI → grub → kernel → container images). Required for IEC 62443-3-3 SL-3.
TPM / HSMTPM 2.0 for key storage + measured boot attestation. Optional HSM (YubiHSM 2, $650) for high-security customers (federal, nuclear, finance).
Our reasoning
These 8 capabilities are the minimum bar for industrial-grade edge. Anything less is "a Raspberry Pi with a Python script" — fine for hobby, not for offshore platforms. The specific design decisions: (1) Store-and-forward is 72 hours, not the 24-hour industry default — offshore platforms can have 24-hour satellite blackouts during storms, and our customers demanded a 3-day buffer; (2) Local alerting never round-trips to cloud — this is the difference between a "cloud IoT" product (AWS/Azure) and an industrial one. The 18 ms RTT to cloud matters when a methane alarm needs to fire in 200 ms; (3) TPM + secure boot is non-negotiable for IEC 62443-3-3 SL-3 compliance, which most oil & gas customers require by 2026.

Ingestion Layer
MQTT brokers, streaming backbone, schema management, security
LAYER 2 / 7
MQTT brokers
Edge → cloud telemetry ingestion
EMQX (prod) / Mosquitto (small)
EMQXProduction broker — 100M+ concurrent connections, MQTT 5.0 + Sparkplug B, Kafka bridge native, rule engine SQL-based, cluster HA. Used for: any deployment ≥ 10K sensors.
HiveMQCommercial alternative — best GUI, best enterprise support, Java-based. Used by: customers with strong Java ops teams who want commercial SLA. ~$50K/year per cluster.
VerneMQErlang-based alternative — solid but smaller community, slower release cadence. We don't recommend for new deployments.
MosquittoFor small deployments (< 10K sensors) — C-based, single binary, 5 MB footprint. Used for: edge-local broker, PoC deployments, single-tenant customers.
Our reasoning
EMQX wins on (a) raw connection count (100M+), (b) Sparkplug B support native (HiveMQ added it later), (c) Kafka bridge out-of-the-box (no custom consumer code), (d) Apache 2.0 license. HiveMQ is the right choice if you need commercial SLA + GUI; for us, the open-source + community trade-off wins. We do not recommend VerneMQ for new deployments — community has shrunk 60% since 2022 and release cadence is slow.
Streaming backbone
Durable, replayable event log
Kafka (prod) / Redpanda (alt)
Apache KafkaDefault — industry standard, KRaft mode (no Zookeeper), exactly-once, 5 brokers minimum for HA. Schema Registry + Kafka Connect ecosystem mature.
RedpandaC++ Kafka-compatible alternative — no JVM, no Zookeeper, 5-10× lower latency, lower memory footprint. Used for: edge + resource-constrained cloud deployments. Community edition free; enterprise adds tiered storage + replication.
Apache PulsarAlternative — supports both queue + log semantics, geo-replication native. Used by: customers with multi-region needs who don't want to use MirrorMaker2. Smaller community than Kafka; more complex ops.
Our reasoning
Kafka is the safe default — 80% of streaming deployments run it, ops tooling is mature, and KRaft mode (no Zookeeper) made it 30% lighter in 2023. We default to Kafka because (a) most customers have a Kafka team already; (b) Kafka Connect has the broadest source/sink connector ecosystem; (c) Confluent's commercial support is available if needed. Redpanda is the right choice for resource-constrained environments — a 3-broker Redpanda cluster fits in 3 GB RAM vs 9-12 GB for Kafka. We use Redpanda at edge sites that need cloud-side streaming. Pulsar is technically superior in some ways (segment-level storage, native geo-replication) but the community is 10× smaller — we recommend it only when geo-replication is a hard requirement.
Schema management
Strongly-typed wire format
Avro + Protobuf + JSON Schema
AvroDefault for Kafka topics — schema evolution with backwards/forwards compatibility, JSON-based schema, smallest payload. Used for: sensor readings, alarms, audit log.
ProtobufFor RPC + cross-language APIs — better code-gen, smaller wire format, gRPC ecosystem. Used for: control-plane messages (provisioning, model deployment), edge ↔ cloud RPC.
JSON SchemaFor human-readable / open APIs — larger payload but tooling-rich. Used for: external API (REST/HTTP), webhook payloads, audit log exports.
Schema RegistryConfluent Schema Registry (open-source) — central authority for Avro + Protobuf + JSON Schema. All Kafka topics enforce schema on write.
Our reasoning
Three schema formats because they have different sweet spots: Avro for high-volume Kafka topics (sensor readings at 100K/sec) — smallest payload; Protobuf for control-plane RPC where you want strong types + cross-language code-gen; JSON Schema for external APIs where humans read the payloads. Using only one is a common mistake — Avro for HTTP APIs is awful (no tooling), JSON Schema for Kafka topics wastes 3-5× bandwidth.
Security
Device identity + transport + topic auth
mTLS + certs + tokens + ACLs
mTLSAll device connections (MQTT, OPC UA, HTTPS) — mutual TLS, customer-specific CA, certs rotated every 90 days. Required for IEC 62443-3-3 SL-3.
Device certificatesX.509 certs provisioned at manufacturing time or via EST (RFC 7030) enrollment. Cert + private key stored in TPM 2.0 — never extractable in cleartext.
Token-based authJWT for user-facing APIs (5-min lifetime, refresh via OAuth2); mTLS for machine-to-machine. Avoid long-lived API keys — they leak.
Topic ACLsPer-device MQTT ACL — each device can only publish to its own topic namespace (e.g., tenant/abc/site-7/sensor/1234/#). Prevents lateral movement if a device is compromised.
Rate limitingPer-device publish rate cap (default 100 msg/sec) — prevents noisy-neighbor + DDoS scenarios. Quota tracked in Redis with sliding-window algorithm.
Quarantine topicsSensors that produce malformed/malformed payloads are auto-quarantined to a separate Kafka topic + the device is throttled. Operator reviews and either fixes or revokes. Prevents poison-message attacks.
Our reasoning
The standard IoT security stack has been mTLS + X.509 + JWT for 5+ years — no surprises. The non-obvious choices: (1) Topic ACLs are the security boundary, not just network isolation — a compromised sensor should only be able to publish to its own namespace, never to other tenants' topics. EMQX supports this natively; (2) Quarantine topics are critical — a single bad sensor can DoS the whole ingest pipeline by spamming malformed Avro. Quarantine + auto-throttle limits blast radius; (3) TPM-stored private keys are required for IEC 62443-3-3 SL-3 — extractable keys in software break the audit chain.

Stream Processing
Real-time transformations, windows, joins, anomaly routing
LAYER 3 / 7
Apache Flink
Primary stream processor
Flink 1.18+ (default)
Use forEvent-time processing with watermarks (handles out-of-order data correctly), exactly-once semantics via 2PC, windowed aggregations (tumbling, sliding, session), stateful joins (sensor stream + maintenance log), ML inference routing (call Hailo-8 edge or cloud model based on liquid placement decision).
Why FlinkTrue streaming (not micro-batch), stateful, exactly-once, savepoints for state migration, robust CEP (Complex Event Processing) for alarm patterns. Industry standard for industrial streaming.
Sizing8 TaskManagers, 4 vCPU + 8 GB each = 32 vCPU + 64 GB total. RocksDB state backend for > 1 TB state. Checkpoint interval 30s, checkpoint to S3.
Our reasoning
Flink vs Spark Structured Streaming: Flink is true streaming (one-event-at-a-time), Spark is micro-batch (process every N seconds). For industrial alarm scenarios where 200 ms matters, Flink wins. Flink's checkpoint mechanism (Chandy-Lamport distributed snapshot) is more mature than Spark's. We use Flink for the main pipeline + savepoints for in-place version upgrades. The complexity tax of Flink is real — 8 TMs with RocksDB tuning is non-trivial ops work — but it's the right tool for safety-critical real-time.
Kafka Streams
Lightweight stream processing
For < 10K sensor deployments
Use forLighter deployments where Flink is overkill — single service, no separate cluster, embedded in the application. State stores via RocksDB, exactly-once via transactions.
LimitationsNo event-time watermarks (processing-time only — bad for out-of-order data), no CEP, no advanced windows. Java-only.
Our reasoning
Kafka Streams is the right answer for "I have 1000 sensors and a small ops team" — runs in your existing Java/Spring Boot app, no Flink cluster to operate. We use it for design-partner PoCs and small customers. Once a customer crosses 10K sensors or needs CEP (alarm pattern detection), graduate to Flink.
Apache Spark Structured Streaming
Batch + stream unified analytics
For batch + ML feature engineering
Use forBatch + stream unified analytics — same code path for "process last 90 days of data" (batch) and "process new data as it arrives" (stream). ML feature engineering pipelines (build features for training + serve same features online).
LimitationsMicro-batch by default (not true streaming); latency minimum ~100ms; less mature watermark handling than Flink.
Our reasoning
Spark Structured Streaming is the right tool for ML feature engineering where you want one codebase for offline training + online serving. We use it for the feature pipeline that builds rolling-window features (24-hour vibration RMS, 7-day alarm rate) — same Spark job runs in batch mode nightly + stream mode continuously. For pure alarm routing + low-latency inference, Flink. Both can co-exist — Flink for hot path, Spark for feature pipeline.

Storage
Hot telemetry, lakehouse, asset hierarchy, graph, cache, search, compliance archive
LAYER 4 / 7
Hot real-time telemetry
Last 90 days, sub-second query
TimescaleDB (default)
TimescaleDBPostgreSQL extension for time-series — hypertables (auto-partition by time), continuous aggregates (materialized views refreshed automatically), compressed chunks (8-12× compression). SQL-native, no new language to learn.
InfluxDBAlternative — purpose-built TSDB, Flux query language. Faster ingest than Timescale at extreme scale (>1M points/sec), but Flux is harder to learn + smaller ecosystem. We use InfluxDB for one design partner who insisted.
QuestDBAlternative — fastest ingest (10M+ points/sec), SQL native, no dependencies. Newer project — community growing fast. Worth watching.
ClickHouseUsed for OLAP analytics — fastest aggregation queries at petabyte scale, columnar, SQL native. NOT a TSDB (no auto-downsampling) but used alongside TimescaleDB for analytical workloads.
Our reasoning
TimescaleDB wins by being PostgreSQL — customers already have a Postgres ops story (backups, monitoring, replication). InfluxDB's Flux query language is the deal-breaker for many customers — they want SQL. ClickHouse is for OLAP analytics (which we use in the lakehouse layer), not for hot telemetry. We use both TimescaleDB (hot, last 90 days) + ClickHouse (analytical, 90 days to 5 years) — different tools for different access patterns.
Analytical lakehouse
Long-term analytics + ML training
Apache Iceberg on S3
Apache IcebergDefault — open table format, schema evolution, time travel, ACID transactions on Parquet files on S3/ADLS/GCS. Native integration with Spark, Flink, Trino, DuckDB.
Delta LakeAlternative — Databricks' format, very similar to Iceberg. Use if you're already on Databricks.
Apache HudiAlternative — best for upsert-heavy workloads (streaming + CDC). Use if your workload is dominated by updates rather than inserts.
Our reasoning
Iceberg vs Delta vs Hudi is mostly a religious war in 2024. We chose Iceberg for: (a) Apache-governed (no single-vendor lock-in); (b) Trino + Spark + Flink all support it natively; (c) Snowflake + BigQuery + Athena all read Iceberg tables now — customer can move between warehouses. Delta is the right choice if you're on Databricks. Hudi is the right choice if your workload is upsert-heavy (e.g., CDC from Postgres). Our workload is insert-heavy time-series, so Iceberg.
Asset hierarchy
Relational store for tags → assets → plants
PostgreSQL
PostgreSQLDefault — battle-tested, JSONB for flexible metadata, mature ecosystem. Used for: asset registry, sensor metadata, maintenance work orders, audit log, user auth.
AvoidMySQL (no JSONB, weaker GEOMETRY, less mature replication), MongoDB (no transactions across collections, no SQL).
Our reasoning
PostgreSQL is the default and we'd need a strong reason to use anything else. JSONB + PostGIS + pg_partman (partition management) + pgvector (embeddings for Graph RAG) all in one database. The Postgres ecosystem is the strongest in databases — Citus for horizontal scale, TimescaleDB for time-series, Supabase for managed Postgres. We use Postgres for everything except time-series (where we split out TimescaleDB on a separate cluster).
Graph relationships
Asset dependency + cause-effect graph
Neo4j (default) / Apache AGE
Neo4jDefault — best-in-class graph database, Cypher query language, mature ecosystem. Used for: Graph RAG (sensor → asset → system → plant), causal inference backtracking, root-cause analysis.
Amazon NeptuneCloud alternative — managed, scales well, supports Gremlin + SPARQL. Use if you're all-in on AWS.
PostgreSQL + Apache AGEIf you want to avoid a separate graph database — AGE adds Cypher to Postgres. Less mature than Neo4j but no separate ops.
Our reasoning
Graph databases are critical for causal inference ("which upstream sensor caused this downstream alarm?") and Graph RAG (LLM retrieves from a graph rather than vector embeddings). We use Neo4j for the depth of Cypher + the maturity of the APOC library. If a customer doesn't want a separate graph database, Apache AGE on PostgreSQL works for the basic cases — it's a good fallback for small deployments.
Fast state / cache
Real-time state + dedup
Redis
RedisDefault — single-threaded but very fast, supports persistence (AOF + RDB), HA via Redis Sentinel or Redis Cluster. Used for: dedup keys, rate-limit counters, alarm state cache, session store, Pub/Sub for live UI updates.
AlternativesDragonfly (drop-in Redis replacement, multi-threaded, faster), KeyDB (similar), Memcached (only if you need pure cache without persistence).
Our reasoning
Redis is the default. Dragonfly/KeyDB are 2024-evolutions that solve Redis's single-threaded bottleneck — useful if you have > 100K ops/sec on a single key. For most industrial workloads, Redis is fine. Memcached if you need pure cache without persistence — but you lose the rich data structures (sorted sets, hyperloglog) that Redis gives you.
Object storage
Blobs, Parquet, models, images
S3-compatible (default)
S3Default cloud — AWS S3 or S3-compatible (MinIO on-prem, GCS for Google, ADLS for Azure).
MinIOFor on-prem / air-gapped — drop-in S3 API, erasure coding, Kubernetes-native. Used in every on-prem deployment.
Azure BlobIf you're all-in on Azure. Same role as S3.
Our reasoning
The S3 API is the de-facto standard — every analytics tool (Spark, Trino, DuckDB, Iceberg) reads S3. Choose your S3-compatible backend based on deployment: AWS S3 in cloud, MinIO on-prem. Avoid Azure Blob's proprietary API if you want portability — ADLS Gen2 is S3-compatible enough.
Search / incidents
Full-text search across alerts, audit log, events
OpenSearch (default)
OpenSearchDefault — Apache 2.0 fork of Elasticsearch, fully open-source, no Elastic license issues. Used for: full-text search across alarms, audit log, events, maintenance records.
ElasticsearchAlternative — mature but moved to SSPL license in 2021 (not Apache 2.0). Some customers avoid for license reasons.
QuickwitEmerging — Rust-based, 10× cheaper for log-scale workloads. Worth watching for 2025.
Our reasoning
OpenSearch is the safe choice — Apache 2.0, AWS-backed, fully compatible with Elasticsearch APIs. We avoid Elasticsearch proper due to the 2021 SSPL license change — some customers can't accept it. Quickwit is the future for log-scale workloads but new; we'll evaluate in 2025.
Compliance archive (WORM)
Immutable audit log for regulators
S3 Object Lock + Glacier
S3 Object LockDefault — WORM (Write-Once-Read-Many) on individual objects, governance or compliance mode, retention period up to 100 years. Used for: EPA-required 5-year retention of emission logs, SEC-required 7-year retention of audit logs, OSHA 5-year retention of injury logs.
AWS Glacier Deep ArchiveCold storage tier — $0.00099/GB-month, retrieval time 12 hours. Used for: archived data > 1 year old that regulators might request.
On-prem WORMMinIO Object Locking + immutable tape (LTO-9). Used for: air-gapped customers who can't use AWS Glacier.
Our reasoning
WORM storage is required for almost every regulatory regime in industrial — EPA, OSHA, SEC, FDA, NERC all require 5-7 year immutable retention. S3 Object Lock is the cheapest path for cloud customers; on-prem customers use MinIO + LTO-9 tape. We do NOT use blockchain for WORM (a common suggestion) — blockchain is overkill for "make sure nobody tampered with last year's audit log".

ML / MLOps
Training, feature store, registry, drift, edge inference
LAYER 5 / 7
ML stack
Training + serving
Python + PyTorch + scikit-learn + XGBoost
PythonThe lingua franca of ML — every library has a Python API. We use Python 3.11+ for ML; Rust for everything else.
PyTorchDefault for TS-FM training — 350M-param transformer, mixed precision (bf16), distributed via FSDP, trained on 8× A100 80GB. Industry standard for foundation models.
scikit-learnFor classic ML — PCA, isolation forest, regression baselines. Used for: quick baselines, feature engineering experiments.
XGBoostFor tabular ML — best-in-class for tabular features. Used for: RUL prediction (remaining useful life) when fine-tuned on a specific asset class.
Our reasoning
Standard ML stack — no surprises. PyTorch (not TensorFlow) because (a) PyTorch has 70%+ research share, (b) Hailo Model Compiler prefers PyTorch, (c) ONNX export from PyTorch is rock-solid. We avoid JAX for now because the ecosystem is still smaller. XGBoost for tabular — LightGBM and CatBoost are alternatives but XGBoost has the broadest deployment (every cloud ML service supports it).
Feature store
Online + offline feature serving
Feast (default) / custom
FeastOpen-source feature store — offline (Iceberg/Parquet) + online (Redis/DynamoDB) feature serving. Decouples feature engineering from model training + serving.
CustomFor customers who want full control — store features in PostgreSQL + Redis, version features with the model. More work but simpler architecture.
Our reasoning
Feast is the only production-grade open-source feature store. Tecton (commercial Feast) is the right choice if you want commercial SLA. Custom is the right choice if your features are simple (e.g., just rolling-window aggregates). We default to Feast + Redis online + Iceberg offline.
Model registry
Versioned model artifacts
MLflow (default)
MLflowDefault — open-source, model versioning, experiment tracking, model stage transitions (staging/prod), deployment integration. Used for every model we ship.
Weights & BiasesCommercial alternative — better UI, better experiment tracking, but $$ for large teams. We use MLflow for the registry + W&B for experiment tracking when budget allows.
Our reasoning
MLflow is the safe default for the registry. W&B is better for experiment tracking (hyperparameter sweeps, run comparison) but expensive. We use both — MLflow for the registry (where the artifact lives), W&B for experiment metadata (how we got there).
Drift monitoring
Detect model degradation
Evidently + Prometheus
EvidentlyOpen-source drift detection — PSI (Population Stability Index), KS-test, KL-divergence, JS-divergence. Generates HTML reports + JSON metrics.
PrometheusMetrics pipeline — Evidently emits Prometheus metrics, Grafana dashboards + Alertmanager for paging. Same observability stack as the rest of the platform.
Our reasoning
Drift detection is a non-trivial part of the ML platform — a 350M-param model can silently degrade if the input distribution shifts. Evidently is the best open-source option; Arize Phoenix is the commercial alternative. We emit drift metrics to Prometheus so alerts integrate with existing ops alerting (no separate ML alerting system).
Edge inference
Run ML on Hailo / Orin / x86
ONNX Runtime + Hailo + TensorRT + OpenVINO
ONNX RuntimeDefault for x86 + Orin — cross-platform, supports CUDA, TensorRT, OpenVINO execution providers. Used for: TS-FM inference on edge x86 servers.
Hailo-8For Hailo accelerator — Hailo Model Compiler converts PyTorch/ONNX to Hailo binary. Used for: TS-FM inference on Hailo-8 (26 TOPS, 2.5 W).
TensorRTFor NVIDIA GPUs — fastest inference on Orin / T4 / A100. Used for: vision pipelines on Jetson Orin.
OpenVINOFor Intel hardware — CPU, iGPU, VPU (Movidius). Used if customer has Intel-only edge hardware.
Our reasoning
We use multiple inference engines because no single engine covers all hardware. ONNX Runtime is the cross-platform default; Hailo SDK for Hailo-8; TensorRT for NVIDIA. We compile each model to multiple targets in the model registry and the liquid placement scheduler picks the best at runtime based on the edge hardware present. ONNX is the lingua franca — every framework exports to ONNX, every hardware vendor supports ONNX.

Observability & Operations
Kubernetes, metrics, logs, traces, infra-as-code, GitOps
LAYER 6 / 7
Kubernetes
Container orchestration
Kubernetes 1.30+
K8sDefault — only sensible choice for cloud-native orchestration in 2024. KubeEdge for edge clusters (single-node k3s also fine for small sites).
AvoidDocker Swarm (deprecated 2020), Nomad (smaller community, fewer features), ECS (AWS-only lock-in).
Our reasoning
K8s won the orchestration war in 2018-2020. We use vanilla K8s (upstream) for portability — customer can run on EKS, GKE, AKS, OpenShift, Rancher, or self-managed. KubeEdge extends K8s to edge — same API, same manifests, just slower (satellite latency for control plane).
Metrics + dashboards
Time-series metrics + visualization
Prometheus + Grafana
PrometheusDefault metrics pipeline — pull-based, TSDB, PromQL query language, Alertmanager for paging. Used for: every component's metrics (Kafka, Flink, edge, ML, custom).
GrafanaDefault dashboard — supports Prometheus + Loki + Tempo + Jaeger + ClickHouse + PostgreSQL + many more. Used for: every ops dashboard.
Our reasoning
Prometheus + Grafana is the de-facto standard for K8s observability. No real alternatives — VictoriaMetrics is a Prometheus-compatible drop-in (faster, less memory) if you hit scale issues. Grafana has competition (Apache Superset, PowerBI) but for ops dashboards, Grafana wins.
Distributed tracing
Cross-service request tracing
OpenTelemetry
OpenTelemetryDefault — CNCF project, vendor-neutral, auto-instrumentation for every language. Used for: tracing MQTT messages through Kafka through Flink through ML inference.
BackendsTempo (Grafana ecosystem, open-source), Jaeger (CNCF, open-source), Datadog (commercial), Honeycomb (commercial).
Our reasoning
OpenTelemetry is the only sensible choice — it's the standard. Vendor lock-in to Datadog or Honeycomb is real (their SDKs instrument differently); OTel gives you portability. We use Tempo as the backend (open-source, Grafana integration).
Logs
Centralized structured logs
Loki (default) / ELK
LokiDefault — Grafana's log aggregation, index by labels only (not full text), 10× cheaper than ELK at scale. Used for: every container log, every application log.
ELK / EFKAlternative — full-text index, more flexible query, but expensive at petabyte scale. Use if you need full-text log search.
Our reasoning
Loki's "index by labels, store logs raw" approach is much cheaper than ELK's full-text indexing. We use Loki for application + container logs (90% of volume); ELK only for the audit log where full-text search is needed. Hybrid is the right answer for most customers.
Infrastructure as code
Reproducible infra
Terraform + Ansible + Helm
TerraformFor cloud infra — VPCs, subnets, IAM, K8s clusters, S3 buckets. Declarative, state file in S3+DynamoDB lock. Multi-cloud via providers.
AnsibleFor bare-metal + edge nodes — provisioning, configuration, application deployment. Agent-less (SSH-based), YAML playbooks. Used for: edge gateway setup, on-prem K8s nodes.
HelmFor K8s application packaging — every component ships as a Helm chart. Used for: deploying SentinelEdge stack itself + dependencies.
Our reasoning
Terraform for cloud, Ansible for bare-metal — this is the standard split. Terraform for bare-metal exists (Terraform-provider-for-Proxmox etc.) but Ansible is better for it. Pulumi (alternative to Terraform, code in TypeScript/Python) is the right choice if your team is JS-native, but the Terraform ecosystem is broader. Helm won the K8s packaging war.
GitOps
Declarative deployments from Git
ArgoCD (default) / Flux
ArgoCDDefault — CNCF graduated, UI-rich, multi-cluster, multi-tenancy, sync waves. Used for: deploying + reconciling every environment from Git.
FluxAlternative — CNCF graduated, lighter-weight, CLI-first, webhooks. Use if you prefer CLI over UI.
Our reasoning
ArgoCD vs Flux is largely taste. ArgoCD has a richer UI + multi-cluster out of the box. Flux is lighter + has better CLI. We default to ArgoCD because customers want the UI for ops visibility. Both work fine — pick the one your team likes.

What we'd pick differently for different customer profiles

  • Small / PoC (≤ 1K sensors, single site): Mosquitto + Kafka Streams (no Flink cluster) + TimescaleDB + Postgres + MinIO + vanilla K8s. Skip: Neo4j, Flink, Iceberg. Saves 80% of ops burden.
  • Mid (1K-50K sensors, multi-site): EMQX + Kafka + Flink + TimescaleDB + Postgres + Neo4j + Iceberg + OpenSearch + Prometheus. Standard stack.
  • Large (50K-500K sensors, multi-region): EMQX cluster + Kafka cluster (5-10 brokers) + Flink cluster (16+ TMs) + TimescaleDB cluster + Postgres cluster + Neo4j cluster + Iceberg on S3 + OpenSearch cluster + Prometheus + Thanos for multi-region metrics. Consider Pulsar if geo-replication is critical.
  • Air-gapped (oil & gas, defense, nuclear): Same as Large but on-prem — MinIO instead of S3, internal CA for certs, no external dependencies. Tape archive for WORM.
  • Edge-only (no cloud): Hailo-8 + K3s + SQLite + DuckDB + local Postgres + local Neo4j. Sync to cloud when WAN available, but run fully autonomous.
