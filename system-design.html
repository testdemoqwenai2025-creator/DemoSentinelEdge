Stage by stage

  1. Sensor samples physics (vibration, temperature, pressure, gas, vision, etc.) and sends readings over MQTT or OPC-UA. Sample rates vary by modality (10 kHz for vibration, 1 Hz for temperature, etc.).
  2. Edge gateway (Hailo-8 or Jetson Orin) decodes the protocol, normalizes to the canonical measurement schema (see schemas/avro/telemetry.avsc), buffers 72 hours locally for WAN-loss resilience.
  3. ingest (FastAPI service, 12 replicas in production) consumes the MQTT/OPC-UA stream, publishes normalized canonical records to Kafka topic telemetry.raw. Idempotent producer, acks=all, zstd compression.
  4. Kafka (5 brokers, KRaft mode, 12 partitions for telemetry.raw) provides the stream backbone. 7-day retention for replay. Schema Registry enforces Avro backward compatibility.
  5. Flink (8 task managers, parallelism 12) consumes telemetry.raw, windows into 30-second tumbling windows per sensor_id, runs TS-FM anomaly detection via ONNX Runtime, emits anomaly tokens (when confidence > 0.85) to alerts.processed.
  6. TimescaleDB (3-node HA cluster via Patroni) stores all canonical measurements as a hypertable, partitioned by day, 30-day retention with continuous aggregates for 1-minute rollups. Queried by the API for hot reads.
  7. API (8 replicas) exposes REST + GraphQL. p99 < 100ms for hot reads. Rate limited at 1000 req/min per IP. JWT auth for write endpoints.
Bandwidth optimization

Anomaly token emission cuts WAN bandwidth by 99.7%. Flink only emits to alerts.processed when TS-FM confidence > 0.85 — most windows produce no output. Raw measurements stay in TimescaleDB for querying; only anomaly events flow downstream.

Why Iceberg?

  • Open table format — no vendor lock-in. Works with Flink, Spark, Trino, Athena, BigQuery, Snowflake.
  • Schema evolution — add columns without rewriting partitions.
  • Time travel — query historical snapshots for debugging or audit.
  • Maintenance operations — compaction, snapshot expiry, branch pruning.

Why ClickHouse for OLAP?

  • Sub-second queries on billions of rows — columnar storage + aggressive compression.
  • Materialized views — pre-aggregated hourly/daily rollups.
  • TTL — automatic expiry at the partition level.
  • SQL interface — familiar to BI teams, integrates with Grafana, Metabase, Superset.

5. Data schemas

Avro (Kafka) + Protobuf (gRPC + storage).

Both formats express the same logical contracts. Avro is used for Kafka wire format (with Schema Registry for evolution). Protobuf is used for gRPC services and storage (more compact, better for streaming).

Canonical telemetry schema

6. ML design

TS-FM + RUL + monitoring.

See AI/ML Stack page for the design and ml/ in the platform repo for the implementation.

Training pipeline

  • Dataset: IndustrialTSDataset loads Parquet files from public corpora (NASA bearings, Case Western Reserve, SECOM, UCI gas turbine, ARPA-E GRIDDATA, UCR/UEA archive), windows into 512-sample chunks with stride 64.
  • Model: 350M-parameter causal transformer (24 layers, 1024 hidden, 16 attention heads). Cross-attention for sensor fusion. Causal-aware loss (PC algorithm validity test).
  • Trainer: AdamW with cosine LR schedule + warmup. Mixed precision (FP16). Gradient accumulation (4 steps). Checkpoints every 1000 steps.
  • Export: PyTorch → ONNX for edge inference (Hailo-8, Jetson Orin).

Inference pipeline

  • Server: FastAPI + ONNX Runtime. Loads model from S3 at startup (cold start < 30s).
  • SLA: p99 < 100ms per inference, batch 32 on Hailo-8.
  • Routing: Liquid placement scheduler routes each inference job to optimal site (edge or cloud) based on latency, bandwidth, drift, battery, carbon.

Monitoring

  • Feature drift (PSI): Population Stability Index per feature. Threshold 0.2 triggers retraining.
  • Confidence distribution: Tracks output confidence over time. Significant shifts indicate data drift or model degradation.
  • Ground-truth feedback: When actual failures occur, compares against predictions, updates per-asset-class confusion matrix. Precision/recall drops trigger targeted retraining.
